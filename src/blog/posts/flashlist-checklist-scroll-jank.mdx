At Delightree, franchise teams work through audits and checklists on their phones, across 150+ brands. A checklist
is a long list of mixed rows: section headers, yes/no questions, notes and photo evidence. Moving those screens from
`FlatList` to Shopify's `FlashList`, along with cutting unnecessary re-renders, made audit screens load about 42%
faster.

That number is from production, and the app's code isn't mine to publish, so this post has no lab repo. It covers
what changes when you switch, the bug the switch brings, and how to check the result on your own list. Everything
about FlashList's API here is from its v2 documentation.

## Why does FlatList struggle with long, mixed lists?

`FlatList` virtualises by mounting and unmounting rows as they enter and leave a window around the viewport. Every row
that scrolls in is a fresh component tree to create, lay out and render on the JavaScript thread. When rows are heavy
(images, inputs, conditional sections) and the user flings the list, the JavaScript thread falls behind and you get
dropped frames, or blank space where rows should be.

## What does FlashList change?

`FlashList` recycles rows instead. A row that leaves the screen isn't destroyed: the same component instance is
re-rendered with the next item's props. Re-rendering an existing tree is much cheaper than building a new one, which
is where the smoother scrolling comes from.

Version 2 changed a lot from version 1:

- **It needs the New Architecture.** The v2 migration guide is explicit that v2 only works on top of it. On the old
  architecture, stay on v1.
- **No more size estimates.** v2 measures items itself, so `estimatedItemSize`, `estimatedListSize` and
  `estimatedFirstItemOffset` are deprecated. You can delete them.
- **Typed refs changed.** A ref is now `FlashListRef<Item>` instead of `FlashList<Item>`.
- **`MasonryFlashList` is gone.** It's now a `masonry` prop on `FlashList`.

## The migration

For most lists the change is the import and the component name:

```tsx title="ChecklistScreen.tsx"
import { FlashList } from "@shopify/flash-list";

<FlashList
  data={items}
  renderItem={renderChecklistItem}
  keyExtractor={(item) => item.id}
  getItemType={(item) => item.kind} // "header" | "question" | "photo"
/>
```

`getItemType` matters most on mixed lists. With it, FlashList keeps a separate recycling pool for each type and never
recycles a row into a different type. A photo row is only ever reused as another photo row, so it re-renders with new
data instead of turning a header into a photo row.

Memoize what you pass in, too. FlashList's docs say memoizing its props matters more in v2, so define `renderItem`
outside the component or wrap it in `useCallback`, and don't build a new `data` array on every render.

## The catch: recycled rows keep their state

Because a row's component instance is reused, any `useState` inside it survives into the next item that row shows.
On a checklist, that looks like this: you expand the note on question 3, scroll down, and question 27 shows up with
its note already expanded, because it's the same component wearing different props. A half-typed answer can move the
same way.

There are two fixes. The first is to keep the state outside the row, in the list's data or a store keyed by item ID.
The second, for state that really belongs to the row, is FlashList's `useRecyclingState`. It works like `useState`
but takes a dependency array, and resets when the dependencies change:

```tsx title="QuestionRow.tsx"
import { useRecyclingState } from "@shopify/flash-list";

function QuestionRow({ item }: { item: Question }) {
  // Starts closed for every question, even when this row was showing another one.
  const [noteOpen, setNoteOpen] = useRecyclingState(false, [item.id]);
  // ...
}
```

It also tells FlashList the row may have changed size, the same way `useLayoutState` does. Use `useLayoutState` for
state that changes a row's height but doesn't need resetting, so the list resizes the row smoothly instead of waiting
for `onLayout`.

<Gotcha title="Don't fix it with a key">
  Putting a `key` that changes per item on a row, or on components inside it, does reset its state, but only by
  forcing a remount, which throws away the recycling you switched for. FlashList's docs warn that a `key` inside items
  "will highly degrade performance".
</Gotcha>

## Lists inside rows: useMappingHelper

React still wants keys when a row maps over an array, like the photo thumbnails on a question. For those, use
`useMappingHelper`. Its `getMappingKey` picks a key strategy that doesn't fight recycling:

```tsx title="PhotoStrip.tsx"
import { useMappingHelper } from "@shopify/flash-list";

function PhotoStrip({ photos }: { photos: Photo[] }) {
  const { getMappingKey } = useMappingHelper();
  return photos.map((photo, index) => <Thumbnail key={getMappingKey(photo.id, index)} photo={photo} />);
}
```

## Keep each recycle cheap

Recycling saves building a tree, but every scrolled row still re-renders. The less a row does on each render, the
smoother the list:

- **Memoize heavy parts that don't depend on the item.** A row's toolbar or icon set can be wrapped in `memo`, so it
  skips re-rendering when the row is recycled.
- **Do the work before the list.** Format dates, work out labels and filter answers once, in the data, rather than in
  every row render.
- **Keep row types honest.** If one type has a dozen visual variants, splitting it into more `getItemType` types
  gives each pool rows that need fewer changes on reuse.

FlashList's own advice is to measure before and after each of these changes, rather than memoizing everything by
default.

## Measure in release builds

FlashList's docs warn that it can look slower than FlatList in development, so compare release builds only. Use a
low-end Android phone, where problems show first, and fling the list from top to bottom and back:

1. **Watch the frame rate.** The Perf Monitor in the dev menu shows UI and JavaScript frame rates; a JavaScript frame
   rate that collapses during a fling is the jank you're fixing.
2. **Look for blank rows.** Blank space while flinging means rows aren't ready in time.
3. **Profile a scroll.** In React Native DevTools' profiler, rows should re-render on scroll, not mount. Rows that
   mount every time usually mean a changing `key` or a missing `getItemType`.
4. **Time the screen.** For a checklist screen, time from navigation to the list showing its first rows, which is the
   load time that improved at Delightree.

Run each check on the old and the new list in the same build setup. Only that comparison tells you what the switch
bought you.

## Before you ship

- The app is on the New Architecture, and FlashList is on v2.
- `estimatedItemSize` and the other estimate props are deleted.
- Mixed lists set `getItemType`.
- No row, or component inside a row, gets a `key` that changes per item; mapped children use `useMappingHelper`.
- Row-local state uses `useRecyclingState`, or lives outside the row.
- `renderItem` and `data` are stable between renders.
- You've compared FlatList and FlashList in release builds, on a low-end Android phone.

## FAQ

### Is FlashList faster than FlatList?

For long lists, and for lists with heavy or mixed rows, usually yes, because it re-renders recycled rows instead of
building new ones. In development it can look slower, so compare release builds. On Delightree's audit checklists,
FlashList and rendering work together made screens load about 42% faster.

### Does FlashList v2 work on the old architecture?

No. FlashList v2 only works on React Native's New Architecture. Apps still on the old architecture should use
FlashList v1.

### Do I still need estimatedItemSize in FlashList v2?

No. v2 measures items itself, and `estimatedItemSize`, `estimatedListSize` and `estimatedFirstItemOffset` are
deprecated.

### Why does a row show the wrong state after scrolling in FlashList?

The row's component was recycled from another item and kept its local state. Reset it with `useRecyclingState`, with
the item's ID in its dependency array, or keep the state outside the row.
